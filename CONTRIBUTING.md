# Contributing

Thanks for your interest! This is a security-focused, from-scratch OS. This
guide explains how we work.

## Ground rules

- Be kind and constructive. See the [Code of Conduct](CODE_OF_CONDUCT.md).
- **`main` must always build and boot.** Every change lands via a pull request
  that passes CI.
- **Docs are part of the change.** Update the matching page in
  [`docs/`](docs/README.md) - and the [threat model](docs/architecture/threat-model.md)
  for security-relevant changes - in the same PR.
- **Authorized use only.** This project is for authorized security testing,
  research and education. Contributions must respect the ethical boundary in
  the [threat model](docs/architecture/threat-model.md): dual-use primitives
  (raw sockets, scanners, fuzzers) are welcome; weaponized malware
  (self-spreading, C2, destructive or mass-exploitation payloads) is not.

## Design decisions are collaborative

Significant or hard-to-reverse choices are **discussed before implementation**,
not decided in a PR after the fact. Open a `type:research` issue or a
Discussion, agree an approach, and record it as an
[ADR](docs/adr/README.md). This applies especially to the security model, the
syscall/IPC surface, and anything touching the TCB.

## The `unsafe` rule

`unsafe` is **forbidden** outside the `hal` crate ([ADR 0007](docs/adr/0007-unsafe-policy.md)).
A PR that adds `unsafe` elsewhere, or weakens `#![forbid(unsafe_code)]`, will
not be merged. In `hal`, every `unsafe` block needs a `// SAFETY:` comment.

## Workflow

1. Fork (maintainers: branch directly). Branch name: `<type>/<issue#>-<slug>`,
   e.g. `feat/12-serial-driver`.
2. Commit with [Conventional Commits](https://www.conventionalcommits.org/) and
   a crate/subsystem scope: `feat(cap): add endpoint capability`.
   **Do not add co-author or "generated by" trailers of any kind.**
3. Make sure these pass locally:
   - `cargo xtask build`
   - `cargo fmt --check`
   - `cargo clippy --all-targets -- -D warnings`
   - `cargo xtask test`
   - the kernel boots: `cargo xtask run`
4. Open a PR referencing the issue (`Closes #12`) and fill in the template.
5. Squash-merge after review and green CI.

## Labels

| Prefix | Meaning |
|---|---|
| `type:` | `bug`, `feature`, `docs`, `chore`, `epic`, `research`, `security` |
| `area:` | subsystem, e.g. `area:hal`, `area:cap`, `area:ipc`, `area:net`, `area:tooling` |
| `priority:` | `critical`, `high`, `medium`, `low` |
| `status:` | `triage`, `blocked`, `needs-design`, `in-progress` |

## Reporting bugs

Use the bug template. Include the commit hash, host OS, Rust and QEMU
versions, and the **full serial log**. For crashes, rerun with
`cargo xtask run -- -d int,cpu_reset -no-reboot` and attach the output.

## Security issues

Do **not** open public issues for vulnerabilities in this OS. See
[SECURITY.md](SECURITY.md).
